# 改进发布说明：从“可展示”到“可复核”的收口

**发布日：2026-08-02；状态：已完成并经真实数据、单元测试和 dbt 验证。** 本文是旧版说明的增量更正：如与较早文件中的数字、候选重复处理或 HGB 一致性表述冲突，以本文及 `data/processed/` 本轮运行产物为准。

## 1. 为什么还要改

项目原本已经能展示完整管道，但为了让它经得起面试追问，仍有六个不能回避的点：候选重复被过早当作确认重复删除；间歇需求没有专门的基线；HGB 回测和未来预测不是同一个训练路径；补货公式没有显式表达库存位置与采购约束；自动化验证缺少真正的端到端链路；看板不能把筛选结果导出。这里的目标不是再堆一个模型，而是把每个结论的口径、代码和验证证据连起来。

## 3. 最新真实数据口径与结果

### 3.1 数据质量

数据源仍为 UCI Online Retail II 两张年度工作表，共 **1,067,371** 行。取消单为 **19,494** 行（1.826%），数量非正/空为 **22,950** 行，价格非正/空为 **6,207** 行，SKU 和交易日期缺失均为 0。全局有效销售日期范围内有 135 天没有交易；非零天占比低于 30% 的 SKU 有 3,135 个。这些计数是标签计数，标签可以重叠，不能相加后推导“总共删除多少行”。

默认需求口径保留 1,041,670 个正向、字段完整的销售行，理由是候选业务键重复不是证明重复录入。严格对照口径保留同键的第一行，得到 1,007,913 行。默认与严格对照的差异不是“已确认损失”，而是需要订单行 ID、业务流程或源系统规则才能定夺的数据不确定性。

### 3.2 预测实验

实验范围为按默认口径销售额排序的 Top 30 SKU，预测粒度为 SKU×日，缺少交易的日子补零。滚动回测有 3 个时间起点，每个起点只使用过去历史来预测其后的 7 天，因此每个完整 SKU、每个模型有 21 个测试日。25 个 SKU 满足完整覆盖；每个模型共 567 个可公平比较的观测。

| 模型 | WAPE | MAE | sMAPE | 预测偏差 | 读法 |
|---|---:|---:|---:|---:|---|
| HistGradientBoosting | 0.7534 | 71.7433 | 1.0251 | 0.0239 | 总体加权误差与绝对件数最佳，但相对误差并非最佳 |
| Croston-SBA | 0.8167 | 77.7663 | 0.9551 | -0.0220 | 间歇需求候选；不在稳定/周期/高波动层参与选模 |
| 7 日移动平均 | 0.8649 | 82.3580 | 0.9679 | 0.0409 | 可解释、平滑的基线 |
| Seasonal naive | 0.9328 | 88.8201 | 0.7582 | 0.0409 | 周期基线，sMAPE 最低但 WAPE/MAE 最差 |

逐 SKU 按 WAPE（再以 MAE、绝对偏差和模型名稳定排序）选择，结果为 **HGB 12 个、移动平均 10 个、seasonal naive 3 个**。这不是“全局冠军模型部署到所有 SKU”。本轮没有满足完整回测的间歇/长尾型 Top 30 SKU，故 Croston-SBA 没有被选中；这是数据范围的事实，不是模型无效的证明。

### 3.3 补货情景

默认演示输入：提前期 7 天、服务水平 95%、现货/在途/预留/欠交均为 0、提前期标准差为 0 天、MOQ 为 0、箱规为 1、单位持有与缺货成本为 0。25 个 SKU 的未来 7 天预测汇总后，提前期需求为 **14,667.97** 件，安全库存为 **12,199.43** 件，ROP 为 **26,867.41** 件，向上取整后的建议量为 **26,879** 件。

这些数值看似具体，但并不是采购建议：默认库存位置人为设为 0，未知库存、在途、预留、欠交、MOQ、箱规、预算、库容和供应商实际提前期。它的正确用途是展示“如果把这些输入补齐，预测误差会怎样进入补货复核”；不可以写成降缺货、增利润、已经下单或已上线。

## 4. 补货公式与边界

1. 库存位置：`IP = on_hand + inbound - reserved - backorder`。它允许为负，表示已有需求占用了供应。
2. 提前期需求：提前期不超过 7 天时，对相应预测日求和；更长时用预测日均值外推。后者是演示简化，真实业务应使用更长预测窗口。
3. 安全库存：`SS = z(SL) × sqrt(L×σe² + μ²×σL²)`。`σe` 为所选模型滚动回测残差标准差；残差不足两条时才退回该 SKU 历史日需求标准差。`σL` 为提前期标准差。默认 `σL=0`，公式退化为经典独立日需求近似。
4. 补货点：`ROP = lead_time_demand + SS`。
5. 理论缺口：`max(0, ROP - IP)`。
6. 建议量：若理论缺口为 0，则为 0；否则先取理论缺口与 MOQ 的较大者，再向上对齐包装倍数。它不含预算、库容、供应商配额、调拨、替代品或订货周期优化。

成本字段只生成 `SS × 单位持有成本` 与 `理论缺口 × 单位缺货成本` 两个可比较代理，绝不等价于实际财务损益，也不自动求最优服务水平。

## 5. 验证证据与尚存风险

本发布实际执行了：`uv run pytest -q`（**17 passed**）；`uv run dbt build --project-dir dbt --profiles-dir dbt`（**7 模型、17 数据测试，24/24 PASS**）；`uv run python -m src.run_pipeline --top-skus 30`（11 项质量审计、9 项重复敏感性、30 候选 SKU、25 可选 SKU、2,268 条回测行、175 条未来预测）；以及 `uv run python -m src.scenarios ...`（25 条情景）。真实链路第一次运行还发现短历史 SKU 特征不足的问题，修复并新增测试后才记录为通过，见开发日志。

仍然存在、且在简历/面试中要主动说明的边界如下：公开数据没有真实库存和采购结果；需求代理无法观察缺货期间的失销；候选重复不能在无订单行 ID 时判真伪；Top 30 的结果不能外推到全 SKU；模型没有促销、价格、节假日、可售状态等外生变量；安全库存采用正态近似且未做服务水平校准；合成端到端测试不能替代生产权限、数据延迟和业务验收。

## 6. 建议阅读与面试讲法

先读 `README.md` 和本文件，再读 `docs/06_end_to_end_project_manual.md` 了解完整过程，接着用 `docs/07_code_and_data_lineage_guide.md` 对照代码。面试时应先说“这是参数化复核工具，不是真实库存优化”，再依次讲数据质量口径、SKU×日/分层、滚动回测、公平选模、残差进入 SS/ROP，以及上线前还需补什么数据。这样可以把项目重点放在严谨的分析决策链，而不是夸大一个 WAPE 数字。
