# 文档深化与交付验收日志｜2026-08-01

## 1. 阶段目标、范围与不做事项

**触发原因**：用户要求“非常详细具体的文档，尤其是开发日志”。此前项目已有完整功能、真实运行结果和基础文档，但日志以摘要形式记录，非代码读者需要跨多个文件才能看到完整的决策、排错和证据链。

**本阶段目标**：把项目文档升级为可审计、可复盘、可面试讲解的交付物。重点是：

1. 每个历史开发阶段都有明确的目标、文件级改动、理由、真实问题、排查、验证、剩余风险和交接；
2. 追溯矩阵能从任一用户要求定位到设计、代码、运行产物和验证结果；
3. 读者不看代码也能理解 SKU×日、分层、滚动回测、指标、情景公式及公开数据边界；
4. 所有新增数值来自当前已生成的 CSV/数据库/先前运行记录；没有重新下载、安装、改系统配置或更改模型逻辑。

**范围外事项**：不修改 Python/SQL/dbt/Streamlit 逻辑，不重跑管道，不改变数据，不重新安装依赖，不启动服务，不下载外部文件。原因是用户当前要求是文档深化，而当前运行产物已通过先前验收；无关重跑会引入不必要变化。

### 本阶段发现的问题与解决过程

**问题 D1：字段名假设与实际 schema 不一致。**

- 现象：第一次只读查询使用 `date` 字段，DuckDB 报错“Referenced column `date` not found”。
- 根因：主题表的实际字段命名为 `demand_date`，不是文档/查询草稿中简写的 `date`。
- 解决：先对真实表执行 `DESCRIBE`，再用 `demand_date` 查询。没有修改数据库或源代码。
- 结果：日级范围成功确认。该问题被转化为文档中的“字段级契约”说明，防止读者把自然语言的“日期”误当作物理列名。

**问题 D2：预测和情景结果的物理位置与临时查询假设不一致。**

- 现象：DuckDB 中没有 `backtest_predictions` 表；随后发现项目输出是 `data/processed/backtest_predictions.csv` 等 CSV。
- 根因：管道的设计是将可交付结果导出为 CSV，而不是把所有 Python 结果回写 DuckDB；早期查询错误假定它们同在数据库中。
- 解决：检查目录和 CSV schema，用 `read_csv_auto()` 做只读复核；更新追溯矩阵与报告中的“产物位置”描述。
- 结果：不再含混地称“结果表”；文档同时说明 DuckDB/dbt mart 与 Python 导出的 CSV 之间的职责边界。

**问题 D3：不同 CSV 的字段不完全相同。**

- 现象：`selected_models.csv` 仅含 SKU、选中模型、WAPE、MAE、偏差；层级在 `daily_demand.csv` 或分层指标产物中。情景表的建议量字段名为 `recommended_order_qty`。
- 根因：每个输出针对不同使用目的，选模表不重复冗余层级字段。
- 解决：报告需要跨表说明的地方明确来源，不虚构“选模表含层级”；情景汇总使用真实列名。
- 结果：数据证据的表级粒度更加明确。

本阶段其余检查**未遇到阻塞问题**。以上三项均为文档事实核对中发现的接口差异，已通过只读检查和措辞修订解决，不影响先前模型、测试或看板的验收结论。

### 验收命令的小插曲（D4）

- **现象**：初次尝试以 Markdown 项目符号 `^- ` 统计简历 bullet，并以二级标题数统计面试问题；命令在简历处返回空结果并提前结束。
- **根因**：这两份交付物实际采用有序编号（`1.`、`2.`……），而非短横线项目符号；20 个问题放在一个“20 个问题与回答要点”章节下，而非 20 个二级标题。这是文档格式选择，不是内容缺失。
- **解决**：直接读取两份文件，并以 `^[0-9]+\. ` 重新统计编号项。
- **复核结果**：`docs/interview_guide.md` 有 20 个编号问题；`docs/resume_bullets.md` 有 5 条编号简历 bullet，满足交付要求。
- **结论**：后续文档验收优先检查内容结构和编号语义，不把单一 Markdown 列表写法误当成内容正确性。
