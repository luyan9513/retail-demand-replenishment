# 项目手册、代码讲解与求职材料扩展日志｜2026-08-02

## 1. 本阶段的用户目标与执行边界

### 用户目标的重新整理

用户希望文档不只是“有结果的说明”，而应当能够同时承担三种角色：

1. **项目说明书**：不看代码也能看懂业务目标、数据来源、每一步处理、模型、补货逻辑、结果和局限；
2. **技术讲解稿**：能解释 Python、SQL、dbt、测试和看板各自为什么存在、如何衔接、关键函数怎样防止错误；
3. **面试复盘材料**：有可直接使用的简历 bullet、不同岗位的表达、不同长度的项目讲解、STAR 故事、常见追问和反问问题。

用户同时要求：每个实际步骤都记录动机、过程和结果；数据处理和分析方法要具体；现有文档已经充分的部分不为“凑篇幅”重复改写。

### 本阶段边界

- **做了什么**：只读审查代码/SQL/产物，新增和更新 Markdown 文档、追溯矩阵与日志；修正发现的文档日期错误；披露实现一致性风险。
- **没有做什么**：没有下载数据、没有安装依赖、没有改系统设置、没有重新运行数据管道、没有修改 Python/SQL/dbt/Streamlit 业务代码、没有改写历史 CSV。
- **为什么这样划界**：当前用户请求是文档完善；现有产物已通过先前数据/测试验收。无关重跑或改代码会改变结果并扩大授权范围。发现的代码风险被如实记录为下一轮实现任务，而不是在文档阶段静默修复。

### 步骤 1：读取文档编写规范和项目现状

- **动机**：需要用统一的结构写长文档，避免只是堆砌表格；同时确认已有材料中哪些已经充分。
- **过程**：阅读文档编写规范；列出 `docs/`、`reports/`、`src/`、`app/`、`dbt/models/`、`sql/`、`tests/` 内的实际文件；完整读取现有项目文档和关键源文件。
- **结果**：确认已有章程、需求、架构、数据、模型、风险、假设、数据卡、模型卡、指标字典、两份报告、4 份历史日志、5 条简历 bullet 和 20 个基础面试问题；主要缺口是“把它们串成一条端到端叙事”和“函数/SQL/测试级技术导读”。

### 步骤 2：只读复核产物，防止用旧文本推测代码行为

- **动机**：文档中涉及回测日期、模型样本数和情景汇总，必须以当前 CSV/数据库的真实字段和值为准。
- **过程**：用项目 `.venv` 中的 DuckDB 对 `data/processed/*.csv` 聚合，并读取 `mart_sku_daily_demand` schema。
- **实际查询结论**：

| 核对点 | 实际结果 | 对文档的影响 |
|---|---|---|
| 主题表日期字段 | `demand_date`，不是临时查询假设的 `date` | 新手册统一使用物理字段名，并解释自然语言“日期”与物理列名不同 |
| 回测训练截止/预测期 | `forecast_origin=2011-11-18` 的实际预测期为 11-19 至 11-25；其余为 11-26 至 12-02、12-03 至 12-09 | 发现并修正两份旧文档中“把训练截止日写入预测期”的错误 |
| 回测行数 | 起点 1/2/3 分别为 588/588/525 行；三模型合计 1,701 | 新手册明确 1,701 不是单模型样本；公平比较是每模型 567 条 |
| 模型行数 | 每个模型均为 567 条正式比较观测 | 正确解释 25 SKU × 3 窗口 × 7 天 |
| 质量审计 | 原始 1,067,371；有效 1,007,913；取消 19,494；候选重复 34,335 等 | 数据处理表只写可复算数字 |

### 步骤 3：审查代码调用链，而不是只读文档描述

- **动机**：用户要求“代码有详细解释”，不能只解释意图，必须解释实际调用关系。
- **过程**：逐模块阅读 `src/ingest.py`、`features.py`、`metrics.py`、`backtest.py`、`train.py`、`replenishment.py`、`scenarios.py`、`run_pipeline.py`、`app/app.py`，以及 5 个 dbt 模型、质量 SQL 和 4 个测试文件。
- **发现 A：导入帮助文本与实现不一致**：`read_source()` 在未传 `sheet_name` 时实际读取所有 Excel 工作表，但 CLI 的 `--sheet` 帮助文字仍写“默认第一张”。本次不改代码，文档明确以实际实现为准，并列为中优先级维护事项。
- **发现 B：HGB 训练路径不完全同构**：
  - 回测：`run_backtest()` 调用 `global_machine_learning_forecasts()`，每个窗口共享一次 HGB，用 SKU one-hot 识别系列；
  - 未来预测：`create_future_forecast()` → `_future_prediction()` 调用 `machine_learning_forecast()`，每个 SKU 单独训练 HGB；
  - 结论：同名 HGB 的回测与未来预测不是完全同一个训练形式。历史回测数值仍有效，但“未来预测由同一已回测模型工件直接产生”的说法不严谨。
- **处理**：将此风险写入新代码导读、模型卡、技术报告、风险台账和追溯矩阵；明确建议下一轮统一训练路径后重跑回测、预测、情景和报告。

### 步骤 4：修正已发现的回测日期文档错误

- **动机**：训练截止日和预测开始日差一天会影响读者是否理解“没有未来泄漏”。
- **原错误**：`docs/04_model_and_experiment_design.md` 与 `reports/technical_report.md` 将第一窗口写作“2011-11-18 至 2011-11-24”。
- **根因**：旧文档把 `forecast_origin`（训练截止日）误表述为预测期第一日，而代码实际测试条件是 `dates > origin`。
- **修复**：改为“训练截止日 2011-11-18；预测期 2011-11-19 至 2011-11-25”；另两个窗口同样后移一天。
- **验证**：对 `backtest_predictions.csv` 按 `forecast_origin` 聚合 `min(forecast_date),max(forecast_date)`，结果与修正文案一致。
- **影响**：不修改代码、CSV 或指标；只修复解释的准确性。
