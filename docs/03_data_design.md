# 数据设计与质量口径

## 来源与主键

原始数据预期字段：`Invoice`、`StockCode`、`Description`、`Quantity`、`InvoiceDate`、`Price`/`UnitPrice`、`Customer ID`、`Country`。原始行无稳定行号时，导入时生成 `source_row_number`；业务去重候选键为发票、SKU、数量、日期、单价和客户的组合，审计中会同时报告“完全重复行”和“候选业务重复行”。

## 有效销售口径

1. `Invoice` 以 `C` 开头：标记为取消单，统计但不进入正向销量。
2. `Quantity <= 0` 或 `UnitPrice <= 0`：标记为异常，进入异常审计表，不进入正向销量。
3. `StockCode` 为空：标记为缺 SKU，不能聚合到 SKU 需求。
4. 完全重复行：保留原始证据，在有效需求表中仅保留第一条，以避免重复计量。
5. 其余有效行：作为正向销售行聚合。

规则优先级为：取消单先判定并保留其数量；再判异常；最后判缺 SKU 与重复。这样一行可能有多个质量标记，但进入需求表必须同时满足有效条件。

## 主题表

### `mart_sku_daily_demand`

粒度为 `stock_code × demand_date`。字段包括销量、销售额、订单数、销售天标记、星期、月份、SKU 销售额、非零天占比、CV、平均非零间隔、需求层级。对选入实验的 Top SKU，日期范围从其最早至最晚有效销售日全量补齐，空销量填 0。

### `mart_sku_forecast`

粒度为 `stock_code × forecast_origin × forecast_date × model_name`。保存真实值、预测值、残差、窗口、需求层级与模型选择，便于重算任何误差指标。

### `mart_replenishment_scenario`

粒度为 `stock_code × scenario_name`。保存参数、提前期需求、安全库存、ROP、假设可用库存、建议量、持有成本代理和缺货成本代理。它只保存假设和演算结果，不代表仓库事实。

## 长尾处理

训练与模型比较默认取销售额前 30 个有效 SKU（可配置 20–50）。其他 SKU 不会被删除：仍在质量与分层统计中，标为间歇/长尾，并建议使用零膨胀/间歇需求策略或改为周级规划；本版不夸大其日级预测精度。

## 字段级数据契约

| 标准字段 | 来源字段示例 | 类型/合法性 | 在本项目中的用途 | 缺失/异常时的处理 |
|---|---|---|---|---|
| `invoice_no` | `Invoice` / `InvoiceNo` | 字符串；可识别 `C` 前缀 | 识别取消单、构造候选业务键 | 缺失仍保留审计，不用于可靠订单统计 |
| `stock_code` | `StockCode` | 去首尾空格后的字符串 | SKU 主键、日级聚合、分层、预测 | 缺失行不能进入 SKU 需求，单独计数 |
| `description` | `Description` | 字符串，可空 | 仅辅助可读性 | 不作为 SKU 身份或预测特征 |
| `quantity` | `Quantity` | 数值 | 正向销量和异常数量判断 | `<=0` 标异常；不进入正向需求 |
| `invoice_date` | `InvoiceDate` | 可解析日期时间 | 聚合为 `demand_date`、回测时间轴 | 缺失/无法解析不进入日级需求，单独计数 |
| `unit_price` | `Price` / `UnitPrice` | 数值 | 销售额、异常价格判断 | `<=0` 标异常；不进入正向需求 |
| `customer_id` | `Customer ID` / `CustomerID` | 字符串/数值，可空 | 候选业务重复键辅助字段 | 不用作预测特征；避免个人标识进入模型 |
| `country` | `Country` | 字符串，可空 | 数据理解与未来扩展 | 本版不做地域分库存结论 |
| `source_sheet`、`source_row_number` | 导入器生成 | 整数/字符串 | 原始溯源、排查重复 | 永远随原始表保留，不作为业务销量字段 |

## 质量规则的优先级、可重叠性与示例

质量标签不是互斥分类。一条记录可以同时是取消单、数量异常和候选重复；审计要保留每个标签的计数，正向需求的准入则使用“必须全部满足”的布尔条件。

| 示例行 | 取消单 | 数量异常 | 价格异常 | 缺 SKU | 候选重复 | 是否进入正向需求 | 解释 |
|---|---:|---:|---:|---:|---:|---:|---|
| 发票 `C123`、数量 `-2`、价格 `3` | 是 | 是 | 否 | 否 | 可能 | 否 | 取消先被识别，负数量也在异常审计中保留 |
| 普通发票、数量 `0`、价格 `5` | 否 | 是 | 否 | 否 | 可能 | 否 | 零数量没有正向需求含义 |
| 普通发票、数量 `4`、价格 `0` | 否 | 否 | 是 | 否 | 可能 | 否 | 零单价不能用于销售额/正向价值口径 |
| 普通发票、数量 `4`、价格 `5`、SKU 空 | 否 | 否 | 否 | 是 | 不适用 | 否 | 无法可靠归属 SKU |
| 两行业务键完全相同 | 否 | 否 | 否 | 否 | 是（后一排名） | 默认只保留排名第一行 | 这是候选去重规则，仍需订单行号确认是否真重复 |
| 普通完整正数行 | 否 | 否 | 否 | 否 | 否 | 是 | 进入 SKU×日聚合 |

## 为什么补零只在实验 SKU 的活跃日期范围内进行

若把所有历史 SKU 统一从项目最早日至最晚日补零，会为停售/新上架/长尾商品制造大量结构性零值，既膨胀表规模，也会把“未销售”与“尚未上市/不可售”混为一谈。因此本项目：

1. 先以有效正向销售额选择 Top SKU；
2. 对每个被选择 SKU，仅在自身最早至最晚有效销售日期间补齐自然日；
3. 补齐后的 `daily_qty=0` 表示该 SKU 在该已观察活跃区间内没有正向成交；
4. 没有把补零解释为真实可售状态，也没有用它推断缺货。

实际运行中，Top 30 SKU 的日级主题表有 19,772 行；全局交易日期轴有 135 个未出现交易的日期。二者说明日历完整性和销售记录完整性不是同一个概念。
