# 求职与面试复盘手册｜零售需求预测与补货决策系统

> 使用方法：投递前先从第 2 节选择对应岗位的表述；面试前练第 3 节的 60 秒/2 分钟讲解；遇到追问时按第 4 节的 STAR 故事和第 5 节的问答结构作答。所有数字都来自本项目 2026-08-01 的本地运行产物；所有情景结果都必须带上“公开数据下的参数化模拟”边界。

## 1. 这段项目经历的正确定位

**一句话版本**：基于 UCI 两年零售交易记录，搭建了从数据质量审计、SKU×日需求分层、滚动回测到安全库存/补货点情景模拟的端到端分析项目，重点展示“预测误差如何支持补货复核”，而非把交易数据包装成真实库存优化。

| 目标岗位 | 最该突出什么 | 不要过度强调什么 |
|---|---|---|
| 数据科学/算法 | 时间泄漏控制、基线比较、HGB、指标冲突、可复现测试 | “模型准确率很高”这类没有业务上下文的表述 |
| 供应链/补货分析 | 提前期、服务水平、SS、ROP、库存位置边界、敏感性 | “系统已自动下单”或“已降低缺货” |
| 零售分析 | SKU 分层、成交需求代理、取消/异常/长尾、销售价值优先级 | 把成交销量说成完整消费者需求 |
| 经营分析 | 指标口径、质量问题、例外清单、管理层沟通、决策边界 | 用没有成本/利润字段的数据推导经营收益 |

## 2. 可直接投递的简历表述

已有精简版见 [resume_bullets.md](resume_bullets.md)。以下按岗位提供可替换的版本；一份简历中保留 3–5 条即可，不要把所有版本同时放进去。

### 2.1 数据科学 / 算法岗版本

1. 基于 UCI Online Retail II 的 **1,067,371** 条交易记录构建 DuckDB + dbt + Python 时序数据管道，完成取消单、数量/价格异常、候选重复、缺失和稀疏 SKU 的 11 项可复现质量审计。
2. 以销售额 Top 30 SKU 构建 **19,772** 行 SKU×日需求主题表，使用非零天占比、平均非零间隔、CV 和 7 日相关性分层，避免用单一模型/单一误差掩盖需求异质性。
3. 采用 3 个 7 天滚动时间窗口比较 seasonal naive、7 日移动平均、Croston-SBA 和共享 HistGradientBoosting；在 25 个完整覆盖 SKU 的 **567** 个公平观测/模型上，HGB 取得 WAPE **0.7534**、MAE **71.7433**，同时保留其 sMAPE 不占优的真实结论。
4. 实现零值安全的 WAPE、MAE、sMAPE、预测偏差函数与 9 项单元测试，验证滚动窗口、滞后特征和补货公式不会泄漏未来信息或在零销量上除零。
5. 将回测残差标准差衔接到安全库存/ROP 情景，并用 Streamlit/Plotly 构建可解释看板；明确区分模型输出、用户假设与未观测业务结果。

### 2.2 供应链 / 补货分析岗版本

1. 将公开零售交易数据从行级记录转为 SKU×日成交需求代理，针对取消单、负/零数量、异常单价、候选重复和长尾商品建立可审计处理规则，形成可用于补货讨论的干净需求口径。
2. 将 SKU 按稳定、周期、高价值高波动和间歇/长尾分层，结合滚动回测误差和预测偏差识别优先复核商品，而不是对全量商品使用统一补货逻辑。
3. 基于未来 7 天预测和回测残差波动，实现服务水平、提前期、库存假设驱动的安全库存、补货点和理论补货缺口计算；默认 7 天/95% 情景覆盖 25 个完整回测 SKU。
4. 设计单 SKU 与组合层面的提前期/服务水平/库存/成本敏感性分析，帮助讨论“缓冲库存、服务目标、资金占用”的取舍，且明确成本仅为代理而非真实最优策略。
5. 主动披露公开数据缺少库存、在途、MOQ、箱规、提前期分布和缺货信息，避免把理论补货量解释为真实采购订单，提出落地前的数据接入清单。

### 2.3 零售分析 / 经营分析岗版本

1. 对 106 万级零售交易行建立数据质量审计，量化取消单 **1.83%**、数量异常 **22,950** 行、价格异常 **6,207** 行和稀疏 SKU **3,135** 个，避免异常交易直接影响销售分析与需求判断。
2. 按成交销售额筛选 Top 30 SKU，并将 30 个商品分为稳定、周期、高波动和间歇需求，输出不同层级的销量节奏、波动和模型误差，支持更细的商品经营复核。
3. 通过 3 个历史时间点回测验证预测策略，发现 HGB 在总体 WAPE/MAE 上更优但 sMAPE 不占优，稳定型聚合偏差为 **-0.0760**，推动从“平均准确率”转向“偏差和业务风险”审阅。
4. 构建 Streamlit 决策看板，串联质量护栏、预测评估、SKU 趋势、参数化补货模拟和例外清单，支持非技术读者从数据问题追溯到决策假设。
5. 编写数据卡、模型卡、指标字典、技术/业务报告和追溯矩阵，使方法、结果、限制与复现命令可被独立审查。

## 3. 三种时长的项目讲解稿

### 3.1 30 秒电梯版

“我做了一个零售 SKU 需求预测和补货决策项目。它不是只画一条预测曲线：我先把 106 万条公开交易数据中的取消单、异常价格/数量和候选重复独立审计，再按 SKU×日构造需求并分成稳定、周期、高波动和长尾。之后用三个滚动时间窗口比较朴素基线、移动平均和 HGB，把每个 SKU 的预测误差和偏差接到安全库存、补货点的参数化情景里。因为公开数据没有真实库存和采购约束，我把结果严格定位为人工补货复核工具，而不是自动下单或利润提升证明。”

### 3.2 2 分钟面试版

“这个项目的目标是展示预测怎么真正支持补货分析，而不是做通用预测 Demo。数据是 UCI Online Retail II，两张表共 1,067,371 行。第一步我没有直接聚合销量，而是把取消单、数量/价格异常、候选重复、缺失字段和稀疏 SKU 做成 11 项质量审计。比如取消单有 19,494 行，占 1.83%；候选重复有 34,335 行，但我明确它不等于系统录入错误，因为缺订单行唯一键。

第二步，我以默认保留候选重复的正向成交为需求代理，同时保留严格去重对照，把销售额 Top 30 SKU 做成连续的 SKU×日表，并按非零天占比、间歇间隔、CV、7 日相关性分层。第三步是严格的时间回测：三个训练截止日，每次用过去预测后面 7 天，绝不随机拆分。比较 seasonal naive、7 日移动平均、Croston-SBA 和共享 HGB 后，只有 25 个 SKU 满足完整 3×7 的验证覆盖。HGB 的总体 WAPE 是 0.7534、MAE 是 71.7433，但 sMAPE 不是最好，稳定型偏差为 -0.0760，所以我保留所有模型和全部指标，而不是只宣传一个最好分数。

最后，我把选中模型的未来 7 天预测和回测残差标准差放进安全库存、补货点和理论缺口公式，并让用户调提前期、服务水平、库存位置、MOQ、箱规和提前期波动。默认库存位置为 0 时的 26,879 件只是情景输出，不是实际下单量。这个边界是我项目里最重视的部分：要落地必须补充真实库存、在途、MOQ、提前期和缺货数据。”

### 3.3 5 分钟深讲结构

1. **业务目标（30 秒）**：不是预测准确率竞赛，而是让补货人员知道哪个 SKU、哪个假设、哪个预测风险需要先复核。
2. **数据质量（60 秒）**：解释为何不直接相加交易数量；给出取消、异常、候选重复和稀疏的具体数字与处理边界。
3. **SKU×日和分层（60 秒）**：解释提前期按天、补零的目的和边界；说明四类 SKU 的规则和为什么不混在一起。
4. **滚动回测和模型（90 秒）**：解释三个训练截止日、下一天开始预测、三种模型、多指标和 21 观测门槛；说清 HGB 总体优点与 sMAPE/偏差限制。
5. **补货情景（60 秒）**：解释 `SS → ROP → Q`，说明参数怎么影响结果、为什么库存=0只是示范。
6. **局限和下一步（40 秒）**：缺真实库存/在途/提前期/MOQ；落地先补数据，再统一回测 HGB 训练形式并验证服务水平。

## 4. 四个可复用的 STAR 面试故事

### 故事 A：把“脏数据处理”讲成业务判断

- **S（情境）**：零售交易数据中同时存在取消单、负/零数量、零价格和相同业务键记录；如果直接聚合，会把交易状态和正向需求混在一起。
- **T（任务）**：建立可解释的正向成交需求口径，同时保留所有问题证据。
- **A（行动）**：在 dbt 中先为每行增加取消、异常、缺失和候选重复标记，再在有效销售层显式使用布尔条件过滤；输出 11 项审计，而不是删除后只报一个“清洗完成”。
- **R（结果）**：从 1,067,371 原始行中得到 1,007,913 有效正向销售行；量化取消单 19,494、数量异常 22,950、价格异常 6,207。重要的是候选重复 34,335 被保留为待确认风险，而没有被包装成确定的数据错误。
- **反思**：真实项目要争取订单行 ID、退货原因和商品状态；数据清洗不是“删掉不喜欢的行”，而是对业务规则负责。

### 故事 B：为什么拒绝随机切分和“只报一个模型分数”

- **S**：需求预测很容易用随机训练/测试切分得到好看的分数，但这不符合补货当天只能看到历史数据的场景。
- **T**：设计一个既能模拟真实决策、又能让不同 SKU 公平比较的评估方式。
- **A**：设置 3 个训练截止日，每次预测其后 7 天；仅保留完整覆盖 3×7 天的 SKU；同时比较 seasonal naive、移动平均和 HGB，并输出 WAPE、MAE、sMAPE、偏差、窗口和分层结果。
- **R**：25 个 SKU、每模型 567 个公平观测。HGB WAPE 0.7534、MAE 71.7433 最好，但 sMAPE 1.0251 不是最低，因此项目选择逐 SKU 选模（12 HGB、10 移动平均、3 seasonal naive）。
- **反思**：面试中主动说出冲突指标，比只报“模型提升”更能体现建模判断。

### 故事 C：从预测误差转向补货复核

- **S**：单纯预测曲线不能回答“这个误差对补货意味着什么”。
- **T**：把预测结果接到一个不会虚构库存事实的决策框架。
- **A**：用回测残差标准差近似不确定性，根据用户输入的提前期、服务水平和库存计算 SS、ROP、理论缺口；再提供单 SKU 和组合敏感性。
- **R**：默认 7 天、95%、库存位置 0 的演示情景中，25 个 SKU 的 SS 合计 12,199.43、ROP 26,867.41、理论建议量 26,879。看板明确显示“模拟”，成本只作代理。
- **反思**：如果没有库存和在途，最负责任的输出不是采购指令，而是“优先复核哪些 SKU、还缺什么参数”。

### 故事 D：性能与方法严谨性的取舍

- **S**：初版为每个 SKU、每个窗口分别训练 HGB，运行耗时过长，不利于本地复现。
- **T**：在不引入未来信息的前提下缩短回测。
- **A**：在每个回测窗口只训练一次共享 HGB，用 SKU one-hot 区分商品，限制树复杂度，并保留逐 SKU 基线和所有指标。
- **R**：完整管道降至约 3 秒；仍输出 1,701 行逐日预测和全部对照模型结果。
- **反思**：代码审计曾发现未来 HGB 采用单 SKU 训练，与共享回测模型并非完全同构；本次已统一两端逻辑并重新验收。好的面试回答应说明修复过程、短历史回退和仍未解决的真实库存数据缺失，而不是声称模型已经生产化。

## 5. 高频追问：用“结论—证据—边界”回答

已有 20 个基础问答见 [interview_guide.md](interview_guide.md)。下面补充面试官更可能继续追问的答案框架。

| 追问 | 先说结论 | 用什么证据支撑 | 主动补充的边界 |
|---|---|---|---|
| 为什么不是直接用 Prophet/深度学习？ | 先做强基线和可复现候选更符合本项目规模 | 三模型滚动回测；HGB 也并非在所有指标上最好 | 没有更多外生变量时，复杂模型不必然胜出 |
| WAPE 0.73 是否“很好”？ | 不能脱离销量量级、SKU、窗口和业务阈值单独评价 | 同时报 MAE、sMAPE、偏差、分层和 SKU 结果 | 公开数据没有服务水平/缺货 KPI 的业务阈值 |
| 为什么不把取消量抵减销售？ | 取消单未必能可靠匹配原销售，而且补货需求应先定义正向成交口径 | 取消单独审计，19,494 行不进入正向需求 | 真实业务可在有退货链路时建立净销量口径作为另一张表 |
| 候选重复为什么直接排除了？ | 是为了避免同键行重复计量，但它是保守的候选规则 | `duplicate_rank=1` 保留，后续行审计 | 没有订单行 ID 时应让该规则可配置，并做敏感性对比 |
| 预测到补货之间缺什么？ | 缺库存位置、在途、实际提前期、MOQ、包装和成本 | 所有情景行都有库存假设/σ来源字段 | 当前输出只能帮助排序复核，不能自动订货 |
| 如何验证服务水平？ | 需要用真实库存与缺货/可售数据做回测 | 当前只有预测残差近似 | 95% 是输入目标，不是本项目证明已达到的结果 |
| 为什么稳定型偏差为负很重要？ | 平均误差可能掩盖系统性低估，低估在补货中更危险 | HGB 稳定型偏差 -0.1263 | 仍不能直接说已缺货，必须结合库存 |
| 你发现的技术债务如何处理？ | 已统一 HGB 回测与未来预测训练形式，并从头验收 | `test_train.py` 调用路径断言、17 pytest、24 dbt 检查 | 仍要补模型注册、漂移监控和真实库存数据 |

## 6. 面试结束可以反问的问题

按岗位选择 2–3 个，避免问官网已有信息。

### 面向数据科学团队

1. 团队在需求预测中更看重全局模型、分层模型还是 SKU 单模型？目前如何处理新品和间歇需求？
2. 线上评估除了 WAPE/MAE 外，会如何连接服务水平、缺货或库存周转？
3. 特征和训练数据是由分析/数据工程团队如何管理版本与回溯的？

### 面向供应链/零售分析团队

1. 目前补货决策使用的是固定安全库存、人工经验，还是会把预测误差纳入服务水平？
2. 库存、在途、MOQ、供应商提前期和促销计划的数据分别由哪些系统维护？
3. 团队对“预测有误差但仍要做决策”通常如何设定人工复核阈值？

### 面向经营分析团队

1. 团队衡量商品经营健康度时，如何平衡销售额、缺货、库存资金和毛利？
2. 数据质量问题（退货、取消、促销、商品上下架）通常由谁定义业务口径？
3. 分析结果从看板到实际动作之间，最常见的阻碍是什么？

## 8. 最终面试原则

这个项目最有说服力的地方不是“做了一个复杂模型”，而是你能证明自己知道：数据哪里不可靠、模型什么时候不该被相信、预测如何进入决策、以及缺什么信息时应该停在“复核建议”而不是越界声称业务收益。把这些边界讲清楚，反而会比单报一个更低的误差分数更像能在真实业务中工作的人。
