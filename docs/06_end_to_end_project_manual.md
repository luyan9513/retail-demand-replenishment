> 这份文档给第一次接手项目的人阅读。目标不是让读者背公式，而是让他能回答：数据从哪里来、每一步处理了什么、为什么这样处理、结果如何进入补货模拟、哪些结论可以说、哪些绝对不能说。若要逐函数阅读代码，请接着看 [代码与数据血缘导读](07_code_and_data_lineage_guide.md)。

> **2026-08-02 发布校正：** 此前版本中“候选重复默认删除、5 模型/20 测试、HGB 未来单 SKU 训练”及其对应数字，已被本次真实全链路重跑取代。当前默认口径保留候选重复并提供严格对照；dbt 为 7 模型/17 数据测试（24/24）；回测和未来预测均使用共享 HGB。请以 [改进发布说明](09_improvement_release_notes.md) 的指标、公式和边界为最终版本。

## 1. 用一句大白话讲清项目

我们拿到的是历史交易记录，而不是库存系统。项目先把交易记录中能代表“正向成交”的部分整理成每个 SKU 每天卖了多少件；再把 SKU 分成稳定、周期、高波动和间歇/长尾几类；然后用过去预测未来的滚动回测，比较简单基线和机器学习；最后把预测量和预测不确定性放进“假设的提前期、服务水平和库存”中，生成**需要人工复核的理论补货缺口**。

它不是一个自动下单系统，也没有证明少缺货、提升利润或已经上线。

## 2. 项目要解决的业务问题与回答边界

| 业务问题 | 本项目如何回答 | 用到的证据 | 不能回答的部分 |
|---|---|---|---|
| 哪些商品值得优先看？ | 按销售价值和需求特征把 SKU 分层，并展示高误差/偏差 SKU | 销售额、CV、非零天占比、平均非零间隔、回测指标 | 哪个 SKU 的真实库存最低或马上会断货 |
| 下一周大概卖多少？ | 对完成完整回测的 SKU 输出未来 7 天的成交需求点预测 | 三个滚动窗口、所选模型、`future_forecast.csv` | 未成交的潜在需求、促销/价格变化后的真实销量 |
| 如果供应商要 7 天到货，应准备多少？ | 在给定库存、服务水平和误差波动下算 SS、ROP、理论缺口 | 预测、残差标准差、用户输入参数 | 可以直接发送的采购订单或实际最优订货量 |
| 模型是否可信？ | 同时报 WAPE、MAE、sMAPE、预测偏差，并按窗口/层级/SKU 拆开 | `backtest_predictions.csv` 和 4 类指标表 | 模型在所有时间、所有商品和未来业务变化下都可靠 |

### 3.2 这份数据有、没有什么

| 数据中有 | 所以本项目可以做 | 数据中没有 | 所以本项目不能假装知道 |
|---|---|---|---|
| 发票、SKU、描述、数量、交易时间、单价、客户、国家 | 历史成交量、成交销售额、周内节奏、取消/负值审计 | 期初/期末库存、可用库存、预留库存、在途 | 库存余额、真实理论缺口、实际可下单量 |
| 取消或负数量信号 | 取消单独立统计、不混入正向销量 | 缺货标记、可售状态 | 未成交需求和缺货损失 |
| 历史交易日期 | 构造日级时间轴、做时间回测 | 供应商、采购订单、收货日期 | 真实提前期分布与供应商绩效 |
| 单价与成交数量 | 以销售额筛选高价值实验 SKU | 成本、毛利、预算、MOQ、箱规、库容 | 利润、成本最优服务水平、采购约束 |

因此，文中“需求”始终是**有效正向成交量的代理**。它很适合展示预测与补货决策框架，却不是完整的潜在市场需求。

### 3.3 进入系统前的字段标准化

`src/ingest.py` 把不同来源的常见列名统一为下列字段。这样 SQL 和 Python 后续不用同时兼容 `Invoice`、`InvoiceNo` 等多种写法。

| 标准字段 | 原始含义 | 用途 | 转换/约束 |
|---|---|---|---|
| `source_row_number` | 导入时生成的顺序号 | 回查原始行、候选重复排序 | 从 1 开始；不是业务订单行号 |
| `source_sheet` | Excel 工作表名 | 证明两张年度表都被导入 | Excel 默认读取所有工作表并合并 |
| `invoice_no` | 发票号 | 取消识别、订单计数、候选重复键 | 转字符串并去首尾空格；以 `C` 开头判取消 |
| `stock_code` | 商品/SKU 编码 | 日级聚合主键、分层、预测 | 转字符串并去首尾空格；为空不得进入 SKU 主题表 |
| `description` | 商品描述 | 候选重复键的辅助字段、人工阅读 | 不用作模型特征或 SKU 主键 |
| `quantity` | 交易数量 | 正向成交需求 | 强转数值；空、0、负值标异常 |
| `invoice_date` | 交易日期时间 | 生成日级日期、回测时间轴 | 转日期时间；无法解析标缺失 |
| `unit_price` | 单价 | 销售额、异常价格判断 | 强转数值；空、0、负值标异常 |
| `customer_id`、`country` | 客户、国家 | 候选重复键/未来分析保留 | 不进入模型，避免使用客户个人标识 |

## 4. 整体数据流：每一步的输入、动作、输出和目的

```text
UCI Excel（两张工作表）
  → 标准化原始交易行（DuckDB raw_transactions）
  → dbt 数据质量标记（取消/异常/缺失/候选重复）
  → 有效正向销售行
  → SKU×日销量和销售额 + 日历补零 + SKU 分层
  → 销售额 Top 30 SKU 的滚动回测
  → 每 SKU 选模型 + 未来 7 天预测
  → 安全库存 / 补货点 / 理论补货缺口情景
  → Streamlit 图表、表格和参数敏感性
```

### 步骤 0：准备运行环境

**动机**：把项目依赖隔离在 `.venv`，不要污染系统 Python；用 uv 管理本机已有 Python。

```bash
uv venv --clear --python 3.12 .venv
uv pip install --python .venv/bin/python -r requirements.txt
```

实际运行使用 Python 3.12.13，安装 92 个包。最初尝试 Python 3.9 时，DuckDB 1.5.5 的实际包要求 Python 3.10+，所以改用本机已有 3.12，而不是下载或替换系统解释器。详细排错见运行日志。

### 步骤 1：导入原始文件到 DuckDB

**命令**：

```bash
.venv/bin/python -m src.ingest --input data/raw/online_retail_II.xlsx
```

| 输入 | 代码做了什么 | 输出 | 实际结果 |
|---|---|---|---|
| `online_retail_II.xlsx` | 读取所有工作表；合并；标准化列名/类型；保留来源工作表和行号；写入 DuckDB | `raw_transactions`、`raw_ingestion_metadata` | 2 张工作表，1,067,371 行 |

**为什么必须先入 DuckDB**：后续 dbt SQL、质量审计和 Python 训练都读取同一个本地数据库，避免每个脚本各自解析 Excel 造成字段或时间口径不一致。

**失败时先检查**：文件路径、文件后缀、关键列是否能映射到 `invoice_no/stock_code/quantity/invoice_date/unit_price`。导入器会明确报缺哪些字段，不会生成不完整表后继续运行。

### 步骤 2：用 dbt 建立数据质量层

**命令**：

```bash
.venv/bin/dbt debug --project-dir dbt --profiles-dir dbt
.venv/bin/dbt build --project-dir dbt --profiles-dir dbt
```

dbt 将数据拆成四层，而不是在一条巨型 SQL 中同时完成全部工作：

| dbt 模型 | 输入 | 处理 | 输出意义 |
|---|---|---|---|
| `stg_online_retail` | `raw_transactions` | 统一 SQL 中的类型和字符串 trim | 后续模型唯一的原始数据入口 |
| `int_sales_line_flags` | staging | 增加取消、数量/价格异常、SKU/日期缺失、`duplicate_rank` 标记 | 原始行仍保留，可审计每个问题 |
| `int_valid_sales_lines` | flags | 只保留取消/异常/关键缺失均通过的行；候选重复默认保留；计算 `line_revenue` | 默认正向成交量口径 |
| `int_valid_sales_lines_deduped` | flags | 在默认有效条件上再保留 `duplicate_rank=1` | 严格候选去重敏感性对照 |
| `int_sku_daily_base` | valid sales | 按 `stock_code + date` 聚合数量、销售额、不同发票数 | 日级主题表的原始聚合 |
| `mart_sku_daily_demand` | daily base | 选 Top 30、补日历、计算统计量和分层 | Python 回测唯一的业务输入 |

实际 `dbt build` 通过 **7 个模型 + 17 个测试 = 24/24**。它验证了关键字段、有效正向销售约束和 SKU×日唯一性，但不等于业务数据没有所有可能错误；例如候选重复是否真的重复仍需要订单行 ID 或业务确认。

### 步骤 3：质量审计：不是“删数据”，而是解释数据

**命令**：

```bash
.venv/bin/python -m src.run_pipeline --top-skus 30
```

该命令先执行 `sql/01_quality_checks.sql`，生成 `data/processed/quality_audit.csv`。质量规则可重叠：一行取消单也可能数量异常；所以不能把各类异常行简单相加再与总行数比较。

| 审计项目 | 判断规则 | 实测值 | 进入正向需求？ | 为什么这样处理 |
|---|---|---:|---|---|
| 原始记录 | 所有导入行 | 1,067,371 | 不适用 | 给所有比例提供分母 |
| 取消单 | `invoice_no` 以 `C` 开头 | 19,494（1.8264%，展示为 1.83%） | 否 | 取消是业务信号，应单独报告，不能与销售混算 |
| 数量异常 | 数量为空或 `<=0` | 22,950 | 否 | 负/零数量没有正向成交量含义 |
| 价格异常 | 单价为空或 `<=0` | 6,207 | 否 | 无法可靠形成正向成交销售额 |
| 缺失 SKU | SKU 空 | 0 | 否 | 无法归属到商品 |
| 缺失交易日期 | 日期空 | 0 | 否 | 无法放入时间序列 |
| 候选业务重复 | 同一业务键中 `duplicate_rank > 1` | 34,335 | 否（只保留第一行） | 没有可靠订单行 ID，故只称“候选”，需业务复核 |
| 有效正向销售 | 同时满足所有有效条件 | 1,007,913 | 是 | 是后续成交需求代理的唯一口径 |
| 无交易日期 | 全局有效日期范围内没有交易 | 135 | 不适用 | 不能直接视为真实关门、断货或数据缺失 |
| 稀疏 SKU | 非零天占比 `<30%` | 3,135 | 仍保留在审计/分层中 | 日级需求过稀，不能和高价值稠密 SKU 混合解读 |

### 步骤 4：构造 SKU×日主题表并补零

**动机**：补货提前期是“几天”，预测窗口也是“7 天”。如果只保留发生交易的日期，模型会误把“没有交易的那天”当成“这天不存在”，无法学习零销量和周内节奏。

**实际做法**：

1. 先对有效正向销售计算每个 SKU 的历史销售额；
2. 选择销售额前 30 个 SKU，限定项目主实验范围；
3. 对每个入选 SKU，从自己的最早有效销售日到最晚有效销售日生成连续自然日；
4. 左连接原日聚合表，没有交易的天填 `daily_qty=0`、`daily_revenue=0`、`daily_orders=0`；
5. 同时计算周几、月份、销售额、非零天占比、CV、7 日相关性和分层标签。

**为什么不是为所有 SKU、所有日期补零**：新品、停售和长尾商品若从全局第一天补到最后一天，会制造大量“商品尚未上市/已停售”造成的假零值。项目只在实验 SKU 的自身活跃区间补零；这仍不能证明当天实际可售，因此不能用补零推断缺货。

实际 `daily_demand.csv` 有 **19,772** 个 SKU×日行，覆盖 30 个 Top SKU。物理字段 `demand_date` 是日期列，`daily_qty` 是日成交量，`demand_segment` 是分层标签。

### 步骤 5：SKU 分层：先承认商品不同，再谈模型

分层不是“给 SKU 贴一个永久标签”，而是用透明规则避免一份总体误差掩盖不同需求形态。判断顺序固定为：

1. 非零天占比 `<0.30` 或平均非零间隔 `>5` 天 → **间歇/长尾型**；
2. 否则，销售额处于 Top 30 内第 75 分位及以上且 CV `>=1.20` → **高价值高波动型**；
3. 否则，7 日滞后销量相关系数 `>=0.35` → **周期型**；
4. 其余 → **稳定型**。

其中 `CV = 日销量标准差 / 日销量均值`；均值为 0 时不计算。实际 30 个实验 SKU 分为：稳定型 18、周期型 4、高价值高波动型 7、间歇/长尾型 1。

### 步骤 6：滚动回测：用过去预测后面的 7 天

**为什么不用随机切分**：把 2011 年的数据随机分给训练集和测试集，会让模型“见过未来时期的模式”，离线分数好看却不模拟真实预测。补货人员在某天做决定时只能看到那天之前的交易。

**代码规则**：每个窗口的训练数据满足 `demand_date <= forecast_origin`，测试数据满足 `forecast_origin < demand_date <= forecast_origin + 7天`；因此 `forecast_origin` 是训练截止日，预测从下一天开始。

| 窗口 | 训练截止日（`forecast_origin`） | 实际预测日 | 所有模型合计行数 | 可预测 SKU 数 |
|---|---|---|---:|---:|
| 1 | 2011-11-18 | 2011-11-19 至 2011-11-25 | 588 | 28 |
| 2 | 2011-11-25 | 2011-11-26 至 2011-12-02 | 588 | 28 |
| 3 | 2011-12-02 | 2011-12-03 至 2011-12-09 | 525 | 25 |

每个窗口要求 SKU 至少有 28 天训练历史，且测试期必须完整 7 天。三个模型合计产生 **1,701** 行逐日回测预测。正式模型比较只用三个窗口都完整的 25 SKU：每模型为 `25 × 3 × 7 = 567` 个公平观测。

### 步骤 7：候选模型、指标与逐 SKU 选模

| 模型 | 预测方式 | 为什么保留 | 实际总体结果（567 观测/模型） |
|---|---|---|---|
| Seasonal naive | 用上一个相同星期位置的销量（主要为 7 天前） | 最容易解释的周周期基线；复杂模型必须与它比较 | WAPE 0.9371；MAE 88.4427；sMAPE 0.7754；偏差 0.0467 |
| 移动平均 | 最近 7 天平均值重复预测未来 7 天 | 平滑短期噪声的基线 | WAPE 0.8668；MAE 81.8123；sMAPE 0.9818；偏差 0.0467 |
| HistGradientBoosting（HGB） | `lag_1/7/14`、7/14 日均值、7 日标准差、周几、月份、SKU one-hot | 测试非线性和跨 SKU 共性是否有用 | WAPE 0.7316；MAE 69.0483；sMAPE 0.9991；偏差 -0.0218 |

HGB 在总体 WAPE/MAE 最好，但 sMAPE 不是最低，所以项目不说“它全面胜出”。最终按每个 SKU 的低 WAPE 选模型；WAPE 缺失才通过排序退到其他条件。结果是 HGB 15 个 SKU、移动平均 8 个、季节性朴素 2 个。

**HGB 为何共享训练**：最初每个 SKU 每个窗口都训练一遍 HGB，实际运行过慢。改为“同一回测窗口只训练一次”：把当时所有合格 SKU 的历史特征合并，并加 SKU one-hot 特征；所有训练行仍早于自己的预测日，所以不引入未来数据。基线仍逐 SKU 计算，树深/迭代被限制。这个取舍提升可复现性，但也必须以完整基线和分层指标约束其解释。

### 步骤 8：生成未来预测和补货情景

只有 25 个完整回测 SKU 才生成未来 7 天预测，得到 **175** 行 `future_forecast.csv`。未来预测使用该 SKU 的选中模型；不确定性输入 `residual_sigma` 优先取该 SKU、该模型历史回测残差标准差，若残差不足 2 个才退回日销量标准差。

补货模块接收：未来预测序列、`residual_sigma`、提前期 `L`、服务水平 `SL`、现货/在途/预留/欠交、提前期波动、MOQ、箱规和持有/缺货单位成本。它计算：

```text
提前期需求 D_L = 前 L 天预测之和；L > 7 时按未来 7 天平均预测外推
库存位置 IP = 现货 + 在途 − 预留 − 欠交
安全库存 SS = z(SL) × sqrt(L×residual_sigma² + 日均预测需求²×提前期标准差²)
补货点 ROP = D_L + SS
理论缺口 = max(0, ROP - IP)；建议量 = 先与 MOQ 比较，再向上对齐箱规
```

默认演示参数为 `L=7`、`SL=95%`、`IP=0`（现货/在途/预留/欠交均为 0）、提前期标准差为 0、MOQ 为 0、箱规为 1、两类成本均为 0。25 个 SKU 的安全库存合计 **12,199.43** 件、ROP 合计 **26,867.41** 件、逐 SKU 向上取整后的理论建议量合计 **26,879** 件。因为 `IP=0` 是演示输入，所有 SKU 都会出现缺口；这正说明它绝非真实订货建议。

| 预测评估 | 模型 WAPE 与 SKU 误差表 | `model_metrics.csv`、`sku_model_metrics.csv` | 看总体、SKU 和偏差，不只看一根柱状图 |
| SKU 预测 | 历史日销量、未来 7 天、近似带 | `daily_demand.csv`、`future_forecast.csv` | 近似带只作风险沟通，不是置信承诺 |
| 补货模拟 | SS、ROP、理论建议量和参数敏感性 | `simulate_replenishment()` | 替换成真实库存/提前期后再作人工复核 |
| 例外清单 | 高 WAPE 或负偏差 SKU、回测覆盖 | `sku_model_metrics.csv` | 排序是人工复核优先级，不等于缺货告警 |

## 5. 数据处理前后：一行记录是如何流动的

以抽象例子说明（不是 UCI 中某条真实订单）：

| 原始情况 | 标记结果 | 是否进入 `int_valid_sales_lines` | 对日级销量的影响 |
|---|---|---|---|
| `Invoice=536365`、SKU=A、数量=6、单价=2.5、日期有效 | 全部有效，`duplicate_rank=1` | 是 | 在该 SKU/日期增加 6 件和 15.0 销售额 |
| `Invoice=C536366`、数量=-6 | 取消、数量异常 | 否 | 只在取消/异常审计中出现，不抵减正向销量 |
| 数量=0、单价=5 | 数量异常 | 否 | 不创造销量或销售额 |
| 数量=5、单价=0 | 价格异常 | 否 | 不创造销量或销售额 |
| SKU 为空 | SKU 缺失 | 否 | 不能聚合到任何 SKU |
| 业务键和前一行完全相同、来源行号更晚 | `duplicate_rank=2` | 否（候选去重） | 不重复计量；仍需业务确认是否确为重复 |
| 某 SKU 活跃期内某日没有任何有效销售行 | 不是原始异常 | 日历 spine 补成零值 | `daily_qty=0`，用于日级时序；不代表真实有货 |

## 6. 读结果时最容易犯的错误

| 错误读法 | 为什么错 | 正确读法 |
|---|---|---|
| “HGB 最好，所以所有 SKU 都用 HGB。” | HGB sMAPE 不占优，且逐 SKU 有基线胜出的情况 | 15/8/2 是回测选出来的实际组合 |
| “取消单和负数量都删了，数据干净了。” | 删除会抹掉问题规模和业务信号 | 原始行保留在审计层，正向需求层才有明确过滤 |
| “34,335 行重复说明系统有 34,335 条录入错误。” | 这里是候选业务键重复，缺订单行 ID 不能下结论 | 只说候选重复，并请求业务补充订单行键 |
| “补零说明当天没卖就是零需求。” | 也可能停售、未上架、不可售或记录问题 | 仅表示活跃区间内无有效正向成交；不可用来推断缺货 |
| “26,879 件就是采购量。” | 默认库存位置为 0，且未知在途、MOQ、箱规、预算 | 只是默认参数下的理论缺口总和 |
| “WAPE 降了就一定降低缺货。” | 离线误差不是缺货率，也不知道库存 | 把负偏差/高误差 SKU 作为优先复核对象 |

## 8. 项目结论与下一步

这个项目已经证明：在公开交易数据上，可以用“质量审计 → SKU 分层 → 时间回测 → 逐 SKU 选模 → 参数化库存情景”的链条，把预测结果变成可讨论的补货复核优先级。

要从作品集变成真实业务系统，下一步必须接入库存位置、在途、提前期分布、MOQ/箱规、库容、成本、促销/价格计划、缺货和到货结果；然后重新回测、校准服务目标，并用上线前后数据验证是否真的影响缺货和利润。
